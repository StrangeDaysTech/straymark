## Baton — release channel + adopter notification for Track C

Track C asks adopters to run `straymark-baton`, but two delivery gaps stood in the way. First, the binary had **no distribution channel**: [`experiment-baton/Cargo.toml`](experiment-baton/Cargo.toml) already declared the intent — *"Experimental: GitHub-release-only (no crates.io publish), mirroring Loom"*, `publish = false` — yet no workflow existed, no `baton-*` release had ever been cut, and the adopter kit's only answers were *"te lo pasamos"* or *"compile it yourself"*. Second, nothing *told* adopters the kit or the channel existed. This PR lands the channel, closes the "binary handoff" item the Track C kit had deferred, and builds the notification stack.

## Changes

### `.github/workflows/release-baton.yml` (new)

Structural mirror of [`release-loom.yml`](.github/workflows/release-loom.yml) (same action versions, same job topology) with the Loom-specific Node/frontend steps removed:

- **Trigger** — `baton-*` tag push or `workflow_dispatch`.
- **Guards** — the tag must start with `baton-`, and `experiment-baton/Cargo.toml`'s version must match the tag, so a skew fails loudly instead of shipping a mislabeled release.
- **Build matrix** — `x86_64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`.
- **Assets** — `straymark-baton-v{version}-{target}.{tar.gz|zip}`.
- **Release** — titled `StrayMark Baton {version} (EXPERIMENTAL)` with `--latest=false`, so the CLI release stays the repo's "latest" and adopter update flows are unaffected.
- **Only-latest posture** — previous `baton-*` releases are deleted, same as Loom (explicit operator decision).

### Version 0.1.0 → 0.2.0

`0.1.0` predates the declared-work-verb turn (#332); the shipped classifier is a different mechanism (declared `work_verb`, no title-scan), so the first real release starts at `0.2.0`. `Cargo.lock` moves mechanically with the bump. No Rust code changes.

### Adopter kit

[`07-track-c-adopter-kit.md`](experiment-baton/07-track-c-adopter-kit.md) §1 preconditions now point adopters at the `baton-*` GitHub release assets (with the four target names); compile-from-source stays as the alternative.

### Adopter notification stack (second commit)

- **[docs/adopters/BATON.md](docs/adopters/BATON.md) (+ es, zh-CN mirrors)** — the durable destination, shaped after LOOM.md: EXPERIMENTAL banner; the declaration-based classification turn (#332); what Track C asks; the binary download table; read-only guarantees; honest limitations. Commands verified against the actual clap subcommands (`classify`, `route --dry-run` — there is no `scan`; caught during drafting). The website needs no change: the docs plugin includes `adopters/**` and its sidebar is autogenerated.
- **WORKFLOWS.md ×3** — a "Declared work routing (Baton, experimental)" subsection next to the existing Loom one.
- **[08-track-c-adopter-announcement-draft.md](experiment-baton/08-track-c-adopter-announcement-draft.md)** — ready-to-post Adopters Discussion: what changed, the four steps (declare → download → sanity-check → calibrate after 2–4 weeks), what's explicitly *not* asked. Posted only after `baton-0.2.0` is cut.

## The adopter answer this unlocks

*"¿Cómo obtengo baton actualizado?"* → download the asset for your platform from the `baton-*` release, extract, put it in your PATH. Future updates = re-cut a tag; the workflow cleans up the old release automatically.
